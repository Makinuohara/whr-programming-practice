# 阶段 7 报告：Agent 辅助开发 200+ 行 WHR 应用

日期：2026-09-26

阶段状态：完成

## 1. 应用概述

`apps/campus_survival/main.whr` 是一个确定性的六周校园生存模拟器。玩家输入姓名，每周从学习、休息、社团、兼职和运动中选择行动，管理能量、知识、金钱、压力、声望和健康，经历状态驱动事件，最后得到行动历史、成就和结局。

程序有 298 个物理行，其中 267 个是非空、非纯注释的有效 WHR 行，超过作业要求的 200 行。行数由 `scripts/count_whr_loc.py` 自动检查，不把空行和纯注释当作代码。

## 2. Agent 开发方式

应用由未参与解释器实现的 Luna Max 编程 Agent 开发。Agent 在任务开始前读取：

- `.agents/skills/whr-language/SKILL.md`；
- Skill 的语法速查和验证流程；
- 冻结语言规范、标准库和错误模型；
- 阶段 6 指南与独立试写证据。

原始任务、约束和命令保存在 `docs/agent_logs/07_app_task.md`；设计、生成、测试、主审返工和结果保存在 `docs/agent_logs/07_app_implementation.md`。

## 3. 语言功能覆盖

| WHR 能力 | 应用中的实际用途 |
|---|---|
| integer/string/boolean/null | 六项数值状态、菜单、条件和 EOF |
| array | 行动历史与成就列表 |
| shape/form | `Player` 和 `ActionResult` |
| 输入输出 | 姓名、菜单输入、状态和报告输出 |
| 分支 | 菜单、事件、成就和结局判断 |
| 循环 | 六周主循环、数组查找 |
| 函数 | 状态规范化、行动、事件、记录和报告 |
| 引用语义 | 函数直接修改 Player 实例及其数组 |

程序没有使用 WHR v1.0 不存在的随机数、时间、文件 I/O 或异常捕获。事件由周次与状态确定，因此固定输入一定产生固定输出。

## 4. 完整用户流程

1. 读取姓名；EOF 时输出说明并正常结束；
2. 创建初始 Player；
3. 每周显示状态和五项菜单；
4. 非法菜单给出提示且不推进周次；
5. 合法行动修改状态并返回 ActionResult；
6. 记录历史，触发确定性事件并更新成就；
7. 六周后展示全部状态、历史、成就和结局。

所有长期数值通过 `normalize_player` 与 `clamp` 控制范围，避免负能量或无限增长破坏模拟。

## 5. 固定演示

`demo_input.txt` 使用顺序：study、rest、club、study、exercise、part-time，六周覆盖全部五种行动，并触发考试周、社团展示和奖学金。

真实运行 stdout 为 2360 字节，与 `demo_output.txt` 逐字一致；stderr 为空，退出码 0。最终关键输出：

```text
Ending: Campus leader ending
=== Simulation complete ===
```

## 6. 主审与返工

初版定义四种结局，但主审计算出 `health <= 0 or stress >= 100` 在六周合法行动中不可达。这个问题不会让演示失败，却会使一条展示在文档中的功能成为死分支。

返工把 burnout 高压阈值调整为 70，并用真实子进程增加三条替代路径：

- 六次兼职：stress 72，`Burnout ending`；
- 六次学习：`Academic survivor ending`；
- 六次休息：`Steady graduate ending`。

原演示仍得到 `Campus leader ending`，因此四种结局全部由合法输入实证可达。

## 8. 验收讲解主线

- 先展示 `Player`：为什么结构比一组零散全局变量更适合保存状态；
- 再展示五个行动函数：每个函数修改引用并返回 `ActionResult`；
- 展示 `clamp`：怎样保证状态不越界；
- 展示 `apply_event`：没有随机数时如何用周次和状态构造可复现事件；
- 展示应用测试：固定输入怎样证明完整流程和不同结局；
- 展示 Agent 返工：自动生成后仍由主智能体检查可达性，而不是只看“能运行”。
