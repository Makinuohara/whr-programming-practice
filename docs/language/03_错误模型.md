# WHR v1.0 错误模型

## 1. 目标

错误必须稳定、可定位、可被黑盒测试验证。诊断面向初学者，不直接暴露 Python traceback。

## 2. 诊断格式

有源码位置的错误统一为：

```text
FILE:LINE:COLUMN: CATEGORY: MESSAGE
```

示例：

```text
demo.whr:3:8: RuntimeError: undefined name 'score'
```

行列均从 1 开始。对于运行时操作，位置指向触发错误的运算符、调用、索引或字段访问；没有更具体位置时指向相关语句起始处。

## 3. 错误类别和退出码

| 退出码 | 类别 | 例子 |
|---:|---|---|
| 0 | Success | 程序正常结束或 `--check` 通过 |
| 2 | UsageError | 参数缺失、未知选项、同时给出多个文件 |
| 65 | LexError | 非法字符、未知转义、未闭合字符串 |
| 66 | ParseError | 缺少分号、括号不匹配、非法赋值目标 |
| 70 | RuntimeError | 类型不匹配、未定义变量、越界、除零、参数数量错误 |
| 74 | IOError | 文件不存在、无权限、文件不是合法 UTF-8 |

命令行用法错误没有源码位置，格式为：

```text
UsageError: MESSAGE
```

文件打开失败格式为：

```text
FILE: IOError: MESSAGE
```

## 4. 错误阶段

1. CLI 先验证参数并读取文件；
2. Lexer 扫描完整源码，遇到第一个词法错误即停止；
3. Parser 遇到第一个语法错误即停止；
4. 只有解析成功才开始执行；
5. Interpreter 遇到第一个运行时错误即停止。

因此词法或语法错误程序不会产生由 WHR 程序语句导致的标准输出。运行时错误发生前已经完成的输出会保留。

## 5. 规范化消息

黑盒测试以完整标准错误文本为准，因此实现使用下列稳定消息模板：

| 情况 | 消息模板 |
|---|---|
| 未定义名称 | `undefined name 'NAME'` |
| 同作用域重复声明 | `name 'NAME' is already declared in this scope` |
| 类型不匹配 | `OP expects EXPECTED, got ACTUAL` |
| 数组越界 | `array index INDEX out of range for length LENGTH` |
| 除零 | `division by zero` |
| 模零 | `modulo by zero` |
| 不可调用 | `value of type TYPE is not callable` |
| 参数数量 | `NAME expects N argument(s), got M` |
| 不存在字段 | `shape 'SHAPE' has no field 'FIELD'` |
| 构造字段错误 | `invalid fields for shape 'SHAPE': MESSAGE` |
| 空数组 pop | `pop expects a non-empty array` |
| 转换失败 | `cannot convert VALUE to integer` |

Lexer 和 Parser 的消息应描述“发现了什么、期待什么”，但行列和类别比自然语言细节更重要。实现冻结后，实际消息将进入黑盒期望文件，之后修改必须作为兼容性变化记录。

## 6. 宿主错误隔离

实现必须把预期的语言错误转换为上述诊断。未预期的解释器缺陷可以在开发模式保留 traceback 供调试，但默认 CLI 不得把 traceback 当成用户错误输出；测试若发现 traceback，视为解释器缺陷。
