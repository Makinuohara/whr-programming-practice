# WHR 语言总体设计与阶段计划

## 1. 项目定位

WHR 是一个面向课程设计的动态类型、解释执行、通用脚本语言。它追求三点：

1. **功能完整**：满足基本类型、数组、结构、输入输出、控制流和函数等硬性要求。
2. **容易解释**：解释器采用经典的词法分析、语法分析、抽象语法树和树遍历执行结构，便于线下讲清楚。
3. **证据完整**：每个功能都对应规范、实现、黑盒测试和可演示示例。

“WHR”作为语言名和文件后缀；其最终释义可以在阶段 1 确认。语言会吸收多种语言的优点，但使用自己的关键字组合、声明/赋值形式和结构定义方式，不完整复刻任何现存语言。

## 2. 暂定语言外观

以下示例用于约束整体方向，不是已经冻结的最终语法：

```whr
# 变量声明与赋值使用左箭头
let name <- "WHR";
let scores <- [92, 88, 95];

# 结构类型
shape Student {
    name;
    score;
}

# 函数
craft average(items) {
    let total <- 0;
    let i <- 0;
    repeat while i < len(items) {
        total <- total + items[i];
        i <- i + 1;
    }
    give total / len(items);
}

let student <- form Student { name: name, score: average(scores) };

when student.score >= 90 {
    show("excellent: " + student.name);
} otherwise {
    show("keep going: " + student.name);
}
```

拟采用的特色组合：

- `let x <- value;` 同时清晰区分声明和赋值方向；
- `shape` 定义结构，`form` 使用具名字段构造实例；
- `craft` / `give` 表示函数与返回；
- `when` / `otherwise` 表示分支；
- `repeat while` 表示条件循环；
- `show`、`read`、`len` 等少量内建函数保持脚本编写简洁；
- 错误信息统一包含错误类别、文件、行列和人类可读说明。

阶段 1 需要明确：完整 EBNF、运算优先级、真值规则、相等性、变量作用域、数组越界、结构字段、函数返回、错误类别和标准库边界。

## 3. 解释器总体架构

```text
源文件 (.whr)
      ↓
词法分析 Lexer       字符 → Token（保留行列位置）
      ↓
语法分析 Parser      Token → AST（递归下降）
      ↓
解释器 Interpreter   AST + Environment → 运行结果
      ↓
标准输出 / 标准错误 / 退出码
```

计划模块：

| 模块 | 职责 | 讲解重点 |
|---|---|---|
| `token.py` / `lexer.py` | 识别关键字、标识符、字面量、运算符和注释 | 最长匹配、行列跟踪 |
| `ast_nodes.py` | 表达式和语句的数据结构 | 语法结构如何变成树 |
| `parser.py` | 递归下降解析和优先级处理 | statement 与 expression 的分层 |
| `environment.py` | 变量作用域链 | 局部变量、函数调用和闭包边界 |
| `values.py` | 函数、结构定义、结构实例等运行时对象 | 语言值和 Python 对象的映射 |
| `interpreter.py` | 遍历 AST 并执行 | 控制流和函数返回的实现 |
| `builtins.py` | 输入输出和基础内建函数 | 宿主能力的受控暴露 |
| `errors.py` | 统一的词法、语法和运行时错误 | 可读错误与非零退出码 |
| `cli.py` | 命令行参数、文件读取和进程行为 | 黑盒测试的稳定接口 |

## 4. 测试策略

测试主体必须是 WHR 脚本。Python 驱动器只负责启动解释器、提供标准输入，以及比对标准输出、标准错误和退出码。

每个用例由以下材料组成：

- `case.whr`：WHR 测试脚本；
- `case.stdout`：期望标准输出；
- `case.stderr`：需要时保存期望错误；
- `case.json`：可选元数据，包括 stdin、期望退出码和标签。

覆盖分为四层：

1. 正常功能：每项语法和语义能够运行；
2. 边界条件：空数组、零次循环、嵌套作用域、递归终止等；
3. 错误行为：非法字符、语法错误、未定义变量、越界和类型错误；
4. 综合回归：多个功能组合，防止局部修改破坏已有行为。

最终命令 `python -m tests.run_all` 必须输出总数、通过数、失败数和每个失败的差异，并以退出码表示结果。

## 5. 性能实验策略

性能测试不以“WHR 必须快于 Python”为目标，而是诚实测量解释器开销并分析原因。

计划至少包含两个相同算法、相同输入的工作负载：

- 计算密集：循环求素数或数值累加；
- 容器密集：数组创建、索引、更新与汇总。

实验协议：

1. WHR 与 Python 采用语义等价算法并产生相同校验结果；
2. 记录 Python 版本、系统、处理器、日期和 Git 提交；
3. 先预热，再交替执行多轮，保留每一轮原始耗时；
4. 报告中位数、最小值、最大值和 WHR/Python 倍率；
5. 区分进程启动总耗时与可选的解释执行耗时；
6. 原始数据保存为 JSON，由脚本生成 Markdown 表格，失败运行不静默删除。

## 6. 200+ 行应用方案

暂定应用为命令行“校园生存模拟器”：玩家在若干周内安排学习、休息、社团和兼职，管理体力、知识、金钱和压力，并经历随机或规则驱动事件，最后按状态计算结局。

它适合作为综合验收程序，因为能够自然覆盖：

- 整数、字符串和布尔值；
- 玩家、事件等结构类型；
- 行动和事件列表；
- 菜单输入、状态输出；
- 多层分支和主游戏循环；
- 状态更新、事件处理、结局计算等多个函数。

完成标准：不少于 200 个 WHR 有效代码行；有说明文档、固定输入的自动演示、至少一条完整通关路径、错误输入处理和 Agent 开发记录。

## 7. 阶段划分与文档交付

### 阶段 0：立项与总体设计（本阶段）

目标：把作业要求转成可执行计划，建立 Git 管理和 Agent 边界。

交付：

- `README.md`
- `PROJECT_STATUS.md`
- `AGENTS.md`
- `docs/00_总体设计与阶段计划.md`
- `docs/00_需求与交付物追踪矩阵.md`

验收：文件互相链接，所有作业要求均进入追踪表，Git 历史从规划开始。

### 阶段 1：语言规范冻结

目标：在写解释器前完整定义 WHR 语法和语义。

交付：词法规则、EBNF、类型与运算、作用域、控制流、函数、结构、I/O、错误模型、示例程序，以及 `docs/stages/01_阶段报告.md`。

验收：仅凭规范可以判断给定程序是否合法、输出是什么；至少准备一组“规范示例—预期行为”表。

建议 Git 提交：`docs: freeze WHR language specification v1`

### 阶段 2：解释器骨架与表达式

目标：实现 CLI、Lexer、表达式 Parser、AST、基本运行环境。

交付：基本类型、变量、算术/比较/逻辑表达式、输出能力和单元级开发验证；`docs/stages/02_阶段报告.md`。

验收：能执行基础示例；词法/语法/运行时错误均有位置和非零退出码。

建议 Git 提交：`feat: implement WHR lexer parser and expression runtime`

### 阶段 3：完整语言运行时

目标：实现数组、结构、输入、分支、循环、函数、作用域和必要内建函数。

交付：完整解释器、功能示例、架构说明和 `docs/stages/03_阶段报告.md`。

验收：六类硬性功能逐项演示；递归、嵌套作用域、break/continue、边界错误行为明确。

建议按能力拆分若干 `feat:` 提交，最后以 `feat: complete WHR language runtime` 收口。

### 阶段 4：完整黑盒测试

目标：以稳定 CLI 接口从外部验证整个语言。

交付：用例目录、Python 驱动器、覆盖清单、失败差异显示和 `docs/stages/04_阶段报告.md`。

验收：一个命令运行全部测试；测试发现数大于零；需求矩阵中每个语言特性至少有正例、边界或错误用例。

建议 Git 提交：`test: add complete WHR black-box suite`

### 阶段 5：性能测试与报告

目标：完成公平、可重复、可解释的 WHR/Python 对比。

交付：等价脚本、基准驱动器、环境快照、原始 JSON、生成的报告和 `docs/stages/05_阶段报告.md`。

验收：结果校验一致；多轮原始数据完整；报告不夸大结论并解释解释器开销。

建议 Git 提交：`bench: compare WHR interpreter with equivalent Python workloads`

### 阶段 6：人类与 AI 开发指南

目标：让没有参与解释器开发的人或 Agent 都能正确编写 WHR 程序。

交付：快速开始、语言手册、惯用写法、调试指南、错误索引、Agent Skill/提示模板、Agent 独立试写记录和 `docs/stages/06_阶段报告.md`。

验收：给新 Agent 一个未见过的小任务，能够只依赖指南生成可通过测试的 WHR 程序。

建议 Git 提交：`docs: add WHR guides for humans and coding agents`

### 阶段 7：Agent 辅助开发 200+ 行应用

目标：使用阶段 6 的指南开发功能完整的综合应用，并保留过程证据。

交付：应用源码、用户手册、固定输入演示、应用测试、有效行数检查、Agent 原始任务与返工记录、`docs/stages/07_阶段报告.md`。

验收：WHR 有效代码行不少于 200；主要功能完整；自动演示和人工交互均成功；开发记录能说明 Agent 的贡献和人工验收。

建议按“设计—可玩版本—测试与文档”分为 `app:` 提交。

### 阶段 8：总验收、发布与 PPT

目标：形成可提交、可演示、可回答问题的最终版本。

交付：系统介绍 PPT/PDF、5—8 分钟讲稿、现场演示脚本、常见问答、最终全量检查报告、发布清单和 Git 标签。

验收：从干净环境按 README 可运行；全量测试通过；基准可复现；应用演示稳定；PPT 结论均有仓库证据。

建议 Git 提交与标签：`docs: prepare final WHR course project delivery`，标签 `v1.0.0`。

## 8. 每阶段统一工作循环

每个阶段都按照以下闭环执行：

1. **范围确认**：读取状态、规范和追踪矩阵，写清本阶段不做什么。
2. **设计**：先完成或更新本阶段设计文档和验收标准。
3. **实现**：按小任务编码，不跨阶段随意扩展。
4. **验证**：运行真实命令，记录发现数、结果与未验证项。
5. **讲解材料**：补充“是什么—为什么—如何实现—如何证明”。
6. **阶段报告**：记录改动文件、关键决策、命令输出摘要、风险和下一步。
7. **Git 收口**：检查差异和状态，提交阶段成果并更新 `PROJECT_STATUS.md`。

阶段报告统一包含：阶段目标、设计决策、完成清单、关键实现、验证证据、问题与解决、当前限制、验收讲解要点、下一阶段接口。

## 9. 评分导向的时间与质量优先级

按分值和风险安排优先级：

1. **30 分应用**：不是最后临时凑行数；在语言和指南稳定后预留完整阶段开发与测试。
2. **20 分测试**：与解释器同步设计，重点展示自动化、覆盖和错误诊断。
3. **20 分解释器**：保证必需功能和清晰架构，避免无评分收益的高级特性拖慢进度。
4. **20 分文档/指南**：规范必须与行为一致，AI 指南要通过新 Agent 实测。
5. **10 分性能**：强调方法公平、结果可复现和原因分析，而不是追求不现实的胜过 Python。

## 10. 最终验收时应能讲清的主线

1. 为什么选择树遍历解释器，以及源代码怎样一步步变成执行结果；
2. WHR 与现有语言相比有哪些自己的语法组合和设计取舍；
3. 变量作用域、函数调用、数组和结构在运行时如何保存；
4. 黑盒测试为何能在不知道内部实现的情况下验证语言；
5. 性能比较如何保证同算法、同输入、多轮运行和结果一致；
6. Agent 指南怎样约束生成代码，以及 200+ 行应用经历了哪些生成、测试与返工；
7. Git 历史如何体现阶段性设计、实现、验证和文档演进。

## 11. 主要风险与控制

| 风险 | 控制措施 |
|---|---|
| 语法边做边改导致实现、测试、文档不一致 | 阶段 1 冻结规范；任何变更三方同步 |
| 解释器功能多但错误处理薄弱 | 从 CLI 起统一错误类型、位置和退出码 |
| 测试看似很多但没有覆盖要求 | 维护需求—测试用例映射并检查发现数 |
| 性能测试不公平或不可重复 | 等价算法、校验输出、环境快照、多轮原始结果 |
| 应用只为凑 200 行 | 先定义用户流程和验收场景，再检查有效行数 |
| Agent 生成记录不完整 | 保存任务、结果、审查、返工和最终验证记录 |
| 验收会运行但讲不明白 | 每阶段同步维护讲解要点，最终进行问答演练 |

## 12. 下一步建议

开启持续执行后，首先进入阶段 1：确认 WHR 的命名释义与语言风格，完成正式 EBNF 和语义规则，再用一批示例程序对规范做纸面推演。该阶段不应提前堆解释器代码，因为规范是后续实现、测试和指南的共同合同。
